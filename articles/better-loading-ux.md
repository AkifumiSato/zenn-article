昨今AI Agentの進化は凄まじく、Figmaからデザインを取り込む精度はもちろんのこと、ある程度AI Agent任せでもそれなりに良いUIが実装できるようになってきました。一方で、細かいUXの作り込みという観点では、AI Agentは明確な指示を必要とします。アニメーション・ローディング・エラー体験などは、指示がなくともある程度よしなに実装してくれることはありますが、筆者の理想とするような作り込みまでしてくれることはありません。これはおそらくモデルやツールの性能的な問題ではなく、プロンプトやルールを通じて行う目標設定の問題です。**AI Agentは実行に特化したツール**であるため、**明確な目標設定はオペレーターである人間側の責務**であり、今後もおそらく人間側の責任が大きい部分だと思われます。

この記事では特に、『ユーザーのストレスを低減するためのローディング体験』をテーマに、筆者が普段意識してる原則やプラクティスについてまとめます。AI Agent時代においても、これらの原則をもとに実装に取り組むことは非常に重要で、AI Agentの活用レベルに差が出る部分だと思われます。

この記事を通して、より良いローディング体験についての学びや考えるきっかけが得られれば幸いです。

## 前提

齟齬が起きやすい部分のみいくつか前提として定義します。

### ローディング

Webアプリケーションにおけるローディングとは、一般的に画面上で何かしらデータの読み込みが発生している状態のことを指します。ページの読み込みやアプリ内遷移、データ操作結果の読み込み待ちなどでローディングが発生しえます。この記事では主にページの読み込みを中心に扱います。

### UI/UX

この記事では、UIとUXを明確に呼び分けています。

- UI（User Interface）: アプリケーションにおける見た目部分を指す
- UX（User Experience）: アプリケーションを通した体験そのものを指す

## 原則1: ローディング時間の最小化

最も良いローディング体験とは即座にコンテンツが表示されることであり、**ユーザーがローディングを体験しない**ことです。

[Response Times: The 3 Important Limits](https://www.nngroup.com/articles/response-times-3-important-limits/)によると、ユーザー体験において留意すべき主な時間制限は3つあります。この記事自体は少々古いものですが、内容自体は現代のWebアプリケーションにも通ずる内容であり、現在でも度々引用されるものです。

> _応答時間に関する基本的なアドバイスは、30年間ほぼ同じである[Miller 1968; Card et al. 1991]。_
>
> - _0.1秒というのは、ユーザーがシステムが瞬時に反応していると感じる限界値であり、つまり、結果を表示する以外に特別なフィードバックは必要ないということである。_
> - _1.0秒は、ユーザーが遅延に気付くものの、思考の流れが途切れることなく維持される限界値と言えるでしょう。通常、0.1秒以上1.0秒未満の遅延であれば、特別なフィードバックは必要ありませんが、ユーザーはデータに直接アクセスしている感覚を失います。_
> - _ユーザーの注意を対話に集中させ続けるには、 10秒程度が限界です。それ以上の遅延が発生すると、ユーザーはコンピュータの処理が完了するまでの間に他の作業を行いたくなるため、コンピュータがいつ処理を完了する予定なのかを示すフィードバックを提供する必要があります。応答時間が大きく変動する可能性がある場合は、ユーザーはいつ処理が完了するのか予測できないため、遅延中のフィードバックは特に重要です。_

アプリケーションが高速にコンテンツを表示できるのであれば、ユーザーにローディングをフィードバックする必要がありません。むしろ、0.1秒で消えるローディングUIは後述するような[チラつき](#原則2-チラつかせない)の原因になり、ユーザーにストレスを与える可能性さえあります。

![ローディング時間と体験](/images/better-loading-ux/user-experience-in-loading.png)

ローディング体験を考える上で最も重要な原則は、**如何にローディングを早く完了するようシステム全体を設計するか**ということにあると筆者は考えています。具体的には、CDNの活用・SQLチューニングなどによるネットワーク通信のボトルネック最適化や、prefetchやキャッシュの活用によるネットワーク通信自体の回避などが有用となります。どの施策が効果的かはアプリケーションによるため、パフォーマンス最適化の大原則である「**推測するな、計測せよ**」に倣い、まずは自身のアプリケーションにおけるボトルネックを精査することから始めることが重要です。

## 原則2: ローディングの分割

前述の通り、理想的な体験は0.1秒以内にコンテンツを表示してローディングを体験させないことです。しかし、全てのコンテンツ表示に対して0.1秒を目標とすることは非現実的です。Hard Navigation^[JavaScript制御を介さない、ブラウザ機能による遷移。]では必ずネットワーク通信が発生し、処理時間やネットワークを最適化するにしても時間的にも金銭的にも限界があります。そのため、コンテンツの表示に時間がかかる場合には、**コンテンツのローディングが適切に分割されていること**が重要となります。

ここでは例として、商品ページのローディングを考えてみます。商品ページのHTMLは以下のように構成されていると仮定します。

| コンテンツ内容           | 静的 / 動的 | データ取得速度 |
| :----------------------- | :---------- | :------------- |
| 静的レイアウト           | 静的        | 無し           |
| 商品情報                 | 動的        | 高速           |
| ユーザー情報やレコメンド | 動的        | 低速           |

データ取得速度に応じてHTTP Streamingを分割（もしくはネットワーク通信を分割）すると、以下のように準備ができた部分から徐々に表示されていくような体験が実装できます。

![分割されたローディング](/images/better-loading-ux/loading-step.png)

ユーザーは、**全ての準備が整ってからページが表示されることを望んでいません**。段階的に準備ができた部分から表示しつつ、どこのコンテンツが読み込み中なのかを知りたいと考えています。上記においてグレーアウトされた部分には、スケルトンなどを配置してローディング中であることを表すと良いでしょう。

## 原則3: チラつかせない

いわゆる**チラつき**（Flicker）は、ユーザーにストレスを与えます。[Core Web Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals?hl=ja)におけるLayout Shiftもチラつきの一種に分類できます。ローディングUIとコンテンツの置き換えの実装は特に、チラつきが発生しないように工夫が必要になります。

ローディング時のチラつき対策には、**スケルトンとアニメーション**の組み合わせが有用だと筆者は考えています。ローディングを表すUIにおいて、スケルトンは最もコンテンツに類するUIです。スケルトンとコンテンツをアニメーションでシームレスに置き換えることで、ユーザーが感じるチラつきを最小限に止めることが可能です。

以下はNext.jsチームが用意した[`<ViewTransition>`のDemo](https://react-view-transitions-demo.labs.vercel.dev/photo/1)におけるスケルトンとコンテンツの入れ替えアニメーションです。

![スケルトンのアニメーション](/images/better-loading-ux/skelton-animation.gif =400x)

gif変換の問題なのか少々ノイズが含まれています。

::::details Next.jsにおける`<ViewTransition>`の実装例

以下は[Next.jsのドキュメント](https://nextjs.org/docs/app/guides/view-transitions#step-2-animate-loading-states-with-suspense-reveals)にある、`<ViewTransition>`と`<Suspense>`を利用したスケルトンのslide-downとコンテンツのslide-upの実装例です。

```tsx
import { Suspense, ViewTransition } from "react";

export default async function PhotoPage({ params }) {
  const { id } = await params;

  return (
    <Suspense
      fallback={
        <ViewTransition exit="slide-down">
          <PhotoContentSkeleton />
        </ViewTransition>
      }
    >
      <ViewTransition enter="slide-up" default="none">
        <PhotoContent id={id} />
      </ViewTransition>
    </Suspense>
  );
}
```

::::

このように、ローディングUIはただ配置すればいいのではなく、ローディングUIとコンテンツの入れ替えを意識してUXを設計する必要があります。

## 原則4: ユーザーを長時間待たせない

チラつき同様にユーザーにストレスを与えるローディング体験として、**長時間ユーザーを待たせること**が挙げられます。原則1の通りローディング時間を最小化することは非常に重要ですが、ローディング時間がどうしても長時間に及んでしまう場合には**期待値調整とフィードバック**も同様に重要となります。いわば、「お待たせしてすいません」というおもてなしの体験です。

前述の通り10秒を超えるとユーザーの集中は途切れてしまうため、10秒を超える場合には適切にフィードバックすることが望ましいと考えられます。具体的なフィードバックとしては、「処理に時間がかかっています。時間をおいてリロードしてください。」というようなダイアログやトーストの表示などが考えられます。

また、昨今ではAIによるコンテンツ生成はじめ、十数秒〜数分かかるような機能を実装することも多々あります。このように明らかに長時間のローディングが見込まれる場合には、ローディングを複数段階に分けて、ユーザーが進捗率を把握できたり、部分的にでも出来上がったものをフィードバックすることが重要となります。

ユーザーを長時間待たせるような場合には、おもてなしの精神で適切なフィードバック体験を作り込みましょう。

## アンチパターン

ローディング体験におけるアンチパターンは様々考えられますが、特に意識が必要なのは**ポップコーンUI**です。ポップコーンUIは画面要素がポップコーンが弾けるように、Layout Shiftなどを伴いながら徐々に画面が完成してく様子を揶揄したものです。

ポップコーンUIについては筆者の過去の記事で詳細に解説してるので、こちらをご参照ください。

https://zenn.dev/akfm/articles/popcorn-ui-anti-pattern

## まとめ

ローディング体験の実装はWebにおけるおもてなしであり、開発者の誠意だと筆者は考えています。人によっては微々たる違いだと感じるかもしれませんが、こういった小さなおもてなしがアプリケーションの満足度向上やストレス軽減につながるはずです。

AI Agent時代においては開発効率が大きく叫ばれ、ツールの使い方やTipsが話題になりがちですが、AI Agentが持ちえない**強い意志やこだわり**こそがこれからの開発者のスキルセットとして重要であり、AI Agentを使ったアウトプット品質に大きな違いを産むことになると筆者は感じています。そういう意味では、この記事が読者にとってユーザーに向き合う姿勢のきっかけになれば、とても嬉しく思います。
